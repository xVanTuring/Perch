# 用 iCloud Drive 同步(不用 CloudKit)— 设计方案

状态:草案,2026-10-28。还没有任何代码。

## 1. 目标和约束

- **不依赖开发者账号**:不用 CloudKit,App 不需要任何 iCloud 权限。数据放在用户自己的
  iCloud Drive 里,换开发者账号、换签名都不影响。
- 多台 Mac 之间同步笔记、分组、图片,以及回收站、归档这些状态。
- **冲突有确定的处理,不悄悄丢数据**:同样的一组文件,每台 Mac 算出来的结果必须一样。
- 不动现有的写入路径:界面和 MCP 仍然只写 Core Data,同步在旁边独立运行。
- 同步文件夹可以换:默认 `iCloud Drive/Perch`,也可以选 Dropbox、Syncthing、坚果云
  客户端同步的文件夹。方案里没有任何只有 iCloud Drive 才有的依赖。

不做:两台 Mac 同时编辑同一段文字时逐字合并(实时协同);iOS 版。

## 2. 核心思路:每台设备只写自己的文件

两台设备改了同一个文件时,iCloud Drive 会自己决定留哪一版,另一版要么变成文件的「冲突版本」,
要么被另存成 `xxx 2.json`。对没有 iCloud 权限的 App 来说,这个过程不透明,也没有可靠的办法
拿回被覆盖的那一版。

所以从根上避开它:**同一个文件永远只有一台设备写**。每台设备有自己的文件夹,只写自己那一份;
读的时候把所有设备的文件合起来。冲突全部由 Perch 在合并时自己判断,iCloud Drive 只负责
搬文件,永远不会遇到「同一个文件两边都改了」。

```
iCloud Drive/Perch/
├─ format.json                        {"format": 1}
├─ devices/
│  ├─ <设备 ID>/
│  │  ├─ device.json                  设备名、App 版本、最后在线时间
│  │  ├─ notes/<笔记 UUID>.json
│  │  ├─ groups/<分组 UUID>.json
│  │  └─ images/<图片 UUID>.json       图片的元数据和删除标记
│  └─ <另一台设备 ID>/ …
└─ blobs/<图片 UUID>.<扩展名>           图片本身,只由创建它的设备写一次
```

一条笔记的最终状态 = 所有设备文件夹里这条笔记的文件合并起来的结果。

图片本身放在共享的 `blobs/` 里不会有问题:图片的 UUID 在粘贴时生成,内容之后不再改变,
只有创建它的那台设备会写这个文件。

## 3. 记录文件的格式

```json
{
  "format": 1,
  "id": "6F1C…",
  "fields": {
    "content":    { "value": "# 购物清单\n- 牛奶", "hlc": "01730106245123-0002-A1B2" },
    "colorIndex": { "value": 3,                    "hlc": "01730106001000-0000-A1B2" },
    "groupID":    { "value": "9D0E…",              "hlc": "01730106001000-0000-A1B2" },
    "isTrashed":  { "value": false,                "hlc": "01730106001000-0000-A1B2" }
  },
  "contentVersion": { "A1B2…": 3, "C3D4…": 1 },
  "deleted": null
}
```

- **每个字段单独带时间戳**,用的是混合逻辑时钟(HLC):`<毫秒时间>-<计数>-<设备 ID>`,
  按字符串就能排序。它以系统时间为主,但保证在本机单调递增;读到其他设备更晚的时间戳时,
  本机时钟会跟上去。所以即使两台 Mac 的系统时间差了几秒,先后顺序也不会乱。设备 ID 放在
  最后用来决胜,两个时间戳永远不会相等。
- **只写本机改过的字段**。没碰过的字段不出现在本机文件里,由其他设备的文件提供。第一次
  开启同步时导出全部字段,**时间戳用这条记录自己的 `updatedAt`,不用当前时间**:否则后加入的
  Mac 只因为导出得晚,就会用自己的旧数据盖掉别的 Mac 之前的修改。代价是开启同步之前的修改
  只能按整条记录比先后,做不到按字段;正文仍由版本向量判断,内容不同就会生成冲突副本,不会丢。
- **正文另外带版本向量 `contentVersion`**:每台设备改一次正文,就把自己那一项加 1,并带上
  它当时已经看到的其他设备的计数。比较两个版本向量就能准确判断两个正文版本是「一先一后」
  还是「互相不知道对方」(同时修改)。
- `deleted`:永久删除的标记,值是删除时的时间戳。

### 同步哪些字段

| 记录 | 同步的字段 |
|---|---|
| 笔记 | `content`、`createdAt`、`updatedAt`、`groupID`、`colorIndex`、`displayOrder`、`isTrashed`、`trashedAt`、`isArchived`、`archivedAt`、`reminderDate` |
| 分组 | `name`、`sortOrder`、`createdAt` |
| 图片 | `fileExtension`、`createdAt`、`ownerNoteID`(数据本身在 `blobs/`) |

窗口相关的字段(`isPinned`、`frameX/Y/W/H`、`hasSavedFrame`、`isCollapsed`)要不要同步,
见第 9 节。

### 设备 ID

安装后第一次开启同步时随机生成,保存在本机的 UserDefaults 里,同时记下这台 Mac 的硬件 UUID。
启动时如果发现硬件 UUID 变了(用迁移助理或 Time Machine 把整台 Mac 恢复到了新机器上),
就生成新的设备 ID,否则两台 Mac 会用同一个 ID 写同一个文件夹。

## 4. 合并规则:冲突怎么解决

合并函数必须满足:不管按什么顺序读到这些文件、读几遍,结果都一样。每台 Mac 读到同一组文件时
就会得到同一个结果,不需要互相协调。

| 情况 | 处理 |
|---|---|
| 两台改了同一条笔记的不同属性(A 改颜色,B 移到别的分组) | 每个字段分别取最新的,两边的修改都保留 |
| 两台改了同一个属性 | 取时间戳大的 |
| 正文:一台改过,另一台之后才改(版本向量一先一后) | 直接用后面的 |
| 正文:两台都改了,但互相不知道对方的修改 | 时间戳大的作为笔记正文;另一版存成一条「冲突副本」笔记(见下文) |
| 两边正文完全相同 | 不算冲突,不管版本向量如何 |
| A 把笔记移进回收站,B 同时改了正文 | 正文的时间戳晚于移进回收站的时间戳 → 自动移出回收站 |
| A 永久删除,B 同时改了正文 | 正文的时间戳晚于删除标记 → 保留这条笔记,放在回收站;否则删除 |
| 笔记被移到的分组已经被删除 | 归到「未分组」 |
| 分组两边同时改名 | 取时间戳大的 |
| 图片 | 只有创建者写;删除只在永久删除笔记时写删除标记(见第 5 节) |

### 冲突副本

- 冲突副本是一条普通笔记,放进固定的「同步冲突」分组,在管理窗口里一眼能看到。正文开头加一行
  说明,下面是落选那一版的完整正文:
  `> 同步冲突 / Sync conflict — iMac, 2026-10-28 06:32 UTC`
- **两台 Mac 会各自发现同一个冲突**,所以冲突副本必须在每台 Mac 上生成得一模一样:
  - UUID 由「原笔记 UUID + 落选版本正文的哈希」算出来(UUID v5),不随机生成。「同步冲突」
    分组的 UUID 也是固定算出来的。
  - 说明行用固定格式:中英文都写,设备名取自落选那台的 `device.json`,时间取落选版本的
    时间戳、统一用 UTC。不能跟随本机的界面语言或时区,否则两台 Mac 写出的文字不同,同一条
    副本又会被当成一次新冲突。
  - 发现冲突的 Mac 把副本作为新记录写进自己的文件夹;两台都写也没关系,内容完全相同,
    不算冲突。
- 冲突副本本身再出现同时修改时,只按时间戳取新的,不再生成「副本的副本」。
- 用户删掉冲突副本后,它的删除标记会一直留着(见第 9 节第 3 条)。只要这个 UUID 有删除标记,
  就不再生成,即使原笔记的冲突还没消失。
- 不会来回打架:原笔记取哪一版只是计算,不往文件里写新版本。哪台 Mac 下次再改这条笔记时,
  新版本向量自然包含了两边,冲突就消失了。

### 以后可以加的:自动合并不重叠的修改

两台改的是同一条笔记的不同段落时,可以用三方合并(以两边共同的上一版为基准)自动合到一起,
只有改到同一处时才生成冲突副本。这需要每台设备在本地保存「上次合并后的正文」作为基准。
放在第三阶段做(见第 11 节),先用冲突副本保证不丢数据。

## 5. 本机这一侧怎么接

### 导出:本机修改 → 本机文件夹

- 读 Core Data 的历史记录(历史记录选项现在本来就开着),找出变了哪些对象、哪些字段,给这些
  字段打上新时间戳,写进本机文件夹里对应的记录文件。
- 同一条笔记在 2 秒内的多次保存合并成一次写入,打字时不会每个字都写一次文件。
- 写文件时先写到 `~/Library/Caches/` 里的临时文件,再整体替换目标文件。临时文件不放在同步
  文件夹里,免得被同步出去。
- 导入时写 Core Data 的操作标记为 `sync-import`,导出时跳过这些操作,不会把刚收到的修改
  又写回去。例外是导入时新生成的冲突副本:它由导入流程直接写进本机文件夹。
- **永久删除**:历史记录里的删除只给 objectID,不带 UUID。所以同步状态库(见下文)要记一张
  objectID → UUID 的对照表,删除时用它找到 UUID,写删除标记。
- 处理完的历史记录要清理掉。现在没有任何代码清理历史记录,只存本地以后它会一直累积。

### 导入:其他设备的文件 → 本机

- 触发时机:同步文件夹的文件变化通知(FSEvents)、启动、从睡眠中唤醒,再加每 5 分钟一次
  全量检查兜底。
- 只读大小或修改时间变了的文件(同步状态库里有缓存),跳过本机自己的文件夹。
- 文件解析失败(还没下载完、格式不认识)就先跳过,下次再试,不当成删除。
- 合并结果在后台 context 里写进 Core Data。写完之后界面怎么刷新,沿用 CloudKit 时期处理远端
  修改的路径(viewContext 自动合并、Spotlight 重新索引、图片 `revision`),实现时要逐个核对,
  包括:别的 Mac 把笔记移进回收站后,本机打开着的浮窗是否会关掉。

### 同步状态库

单独一个 SQLite 文件 `~/Library/Application Support/Perch/SyncState.sqlite`,不放进主数据模型,
这样不用升 schema 版本,也不受 CloudKit 的模型限制。里面存:

- 每条记录每个字段的最新时间戳、正文的合并后版本向量;
- 本机文件夹里每个文件最后写入的内容摘要(没变就不重写);
- 其他设备每个文件的大小和修改时间(没变就不重读);
- objectID → UUID 对照表;
- 本机的 HLC 状态、已处理到的历史记录位置。

这个库丢了或坏了可以重建:清空后全量读一遍所有文件。两边内容相同的不会算冲突,所以重建
不会凭空产生冲突副本。

### 图片

- 粘贴图片时:写 `blobs/<UUID>.<扩展名>`,再写本机的 `images/<UUID>.json`。
- 其他 Mac 先收到图片、后收到引用它的笔记是正常的,和 CloudKit 时一样。**不做全库孤儿图片
  清理**(原因见 CLAUDE.md「Note images」一节)。
- 删除只走现有的四条永久删除路径:它们删掉本地图片的同时写删除标记;写删除标记的那台 Mac
  负责删掉 `blobs/` 里的文件。其他 Mac 读到删除标记后删本地的。

## 6. iCloud Drive 特有的处理

- 默认路径 `~/Library/Mobile Documents/com~apple~CloudDocs/Perch/`(Finder 里显示为
  「iCloud 云盘/Perch」)。Perch 没开沙盒,应该可以直接读写,不需要权限,**待验证**。
- 开了「优化 Mac 储存空间」后,文件可能只在云端,本地只有占位。读这种文件会触发下载并等待,
  所以所有文件读写都放在后台队列,并设超时。
- 文件名不用 `.` 开头,也不用 `.nosync` 结尾(iCloud Drive 不同步这类文件)。
- 不认识的文件名(比如 iCloud Drive 自己改名生成的 `xxx 2.json`)直接忽略并记日志。按第 2 节
  的设计,正常情况下不会出现。
- 格式版本:`format.json` 和每个文件里都有 `format`。读到比本机新的格式就停止同步,提示
  用户更新 Perch,不去改看不懂的数据。
- 没登录 iCloud 或关了 iCloud 云盘:设置里显示原因,同步暂停,本地使用不受影响。

## 7. 第一次开启和新设备加入

- 第一台开启同步的 Mac:把本地全部记录导出到自己的文件夹。
- 之后加入的 Mac(本地已经有笔记):导出自己的,同时读入其他设备的。
  - 两边相同的笔记(比如 2.8.0 之前靠 CloudKit 同步过的)直接合并,不算冲突。
  - 2.8.0 之后两台各自改过的笔记会变成冲突副本,两边的内容都在。
- 第一次合并完弹一个总结:「合并了 N 条便签,其中 M 条有冲突,已放进『同步冲突』分组」。

## 8. 设置界面

新的「同步」页:

- 开关「通过 iCloud 云盘同步」。**用新的设置 key**,不复用 `SettingsKey.iCloudSyncEnabled`
  (用过 CloudKit 同步的 Mac 上它还是 true)。
- 同步文件夹:默认 iCloud 云盘/Perch,可以改成任意文件夹;「在 Finder 中显示」。
- 状态:上次同步时间、待上传数量、冲突副本数量、最近的错误。
- 设备列表:设备名、最后在线时间;可以移除很久没上线的设备(删掉它的文件夹)。

## 9. 待你决定

1. **窗口状态要不要同步**:是否打开成浮窗(`isPinned`,兼作「启动时自动显示」)、窗口位置大小、
   折叠状态。CloudKit 时期这些是同步的。建议**不同步**:每台 Mac 的屏幕不一样,而且在一台上
   打开浮窗,另一台跟着弹出窗口多半不是想要的;笔记归属哪块显示器(`NoteDisplayStore`)本来
   就只存本机。
2. **冲突副本放哪**:建议放进单独的「同步冲突」分组,不用改数据模型。另一种做法是留在原分组、
   加一个「冲突」标记,这要给 Note 加字段(升 schema 版本)。
3. **永久删除标记保留多久**:建议永久保留,每条只有几百字节。如果过一段时间清掉,一台长期
   没开机的 Mac 回来时,会把已经删掉的笔记又带回来。

## 10. 先验证再动手

下面几点决定方案能不能成立,写正式代码前先各用一个小程序在两台 Mac 上验证:

1. 没有 iCloud 权限、没开沙盒的 App 写进 `com~apple~CloudDocs/Perch/` 的文件,能正常同步到
   另一台 Mac。
2. 开着「优化 Mac 储存空间」时,读一个只在云端的文件会自动下载,读之前能判断它是否已下载
   (`URLResourceKey.ubiquitousItemDownloadingStatusKey` 对这种 App 是否可用)。
3. 另一台 Mac 的修改下载到本机时,FSEvents 会通知到。
4. 大概的同步延迟:一台写入后,另一台多久能看到。
5. 几百个小 JSON 文件时,全量检查一遍要多久。

## 11. 分阶段

1. **第一阶段,能用**:文件格式、设备文件夹、导出、导入、字段级合并、删除标记、图片、设置页开关。
   正文同时修改时生成冲突副本。
2. **第二阶段,好用**:冲突处理界面(冲突副本和原笔记左右对比,按钮「用这一版」「保留原来的」),
   设备管理,首次合并总结。
3. **第三阶段**:不重叠修改的三方自动合并。

## 12. 测试

- 合并函数是纯函数,不碰文件和 Core Data,直接写单元测试。重点测:把同一组记录按随机顺序、
  重复多次合并,结果都一样。
- 在测试里用几个临时文件夹模拟多台设备,不需要 iCloud,就能跑完整的导出、导入、冲突流程。
- 最后在两台真实的 Mac 上跑一遍第 4 节表格里的每一种情况。
